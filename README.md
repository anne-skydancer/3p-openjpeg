# CPU-only AVX2 OpenJPEG packages

Windows x64 and Linux x86_64 packages use AVX2 CPU decoding and encoding. CUDA and OpenCL backends are explicitly disabled; no GPU SDK is required. These packages require AVX2-capable processors. The macOS viewer package pin remains separate.

Windows ships openjp2.dll and its import library; Linux ships libopenjp2.a. Existing Autobuild layouts and the openjpeg package name are retained. Release builds preserve precise floating-point behavior and Windows LTO. Codec tools verify the shipping library before packaging. BUILD_POLICY.txt records the intended backend and ISA; SOURCE_REVISION.txt identifies the source.

The measured AVX2 improvement over SSE2 was small and workload-dependent; this package does not claim a viewer FPS improvement. GPU backends cannot be re-enabled at runtime through environment variables.

The source is the fork's `vkstorm-2.5.4-hotfix` line: OpenJPEG 2.5.4 (fork `3b1a6a96`) with decoder fixes for cut downloads, hostile codestreams and the decoder's resource limits.

- **Complete codestreams** decode bit for bit as before, with two exceptions: three 9/7 decodes at a reduced resolution that failed now decode (tiles that vanish at the decoded resolution: ISO p1_06 at reduce 2 and 3, p1_05 at reduce 5), and a codestream whose last tile-part has Psot = 0 but that does not end with an EOC marker keeps its last 2 bytes as tile data.
- **Cut codestreams, non-strict decoding** (the viewer's mode): every complete codeword segment is kept, with or without EPH markers, with packet headers in-band or packed in PPM or PPT, and with a last tile-part of Psot = 0. A packet whose header the data cuts, or whose EPH marker it leaves out, counts as absent; a code-block that loses passes gets no more. Once a tile's data and its packed headers are used up, the remaining packets are not visited. Strict decoding is unchanged.
- **Limits**: a new additive API, `opj_decoder_limits_init()` with `opj_decoder_set_limits()` (`OPJ_HAVE_DECODER_LIMITS`), set after `opj_setup_decoder()` and before `opj_read_header()` (later calls fail). `OPJ_DECODER_LIMITS_SL_TEXTURE`, the Second Life texture profile, allows 1,024 tiles, 8 components (also those a JP2 palette makes), 64 layers, 2,048 pixels per side at the decoded resolution and 256 MiB per decode, counted from the headers before anything is allocated, over all tiles of the decode. Every texture in a 60,045-texture viewer cache passes it. Without limits a decoder keeps OpenJPEG's own bounds, so in non-strict mode some hostile codestreams take longer than in the shipped build (CVE-2023-39327's reproducer runs about 9 s instead of failing in 11 ms): a caller that decodes untrusted data in non-strict mode sets the limits, and the viewer selects `OPJ_DECODER_LIMITS_SL_TEXTURE` in the same change as this package and checks both calls' results.
- **Other fixes**: a reduce factor set after the header is checked before it changes the decoder (upstream #1631), and tile parameters are allocated only for tiles that appear.
